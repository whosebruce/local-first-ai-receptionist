# AGENT_INSTALL — runbook for coding agents

You are a coding agent installing the Local-First AI Receptionist for your
operator ("the owner"). Follow this file exactly. It is written so that a
copy/paste of the whole file into an agent session is safe.

## Hard rules (do not reinterpret)

1. **Never enable outbound sending.** Do not set `outbound.enabled: true`, do
   not edit that key, do not suggest a diff that sets it. Live activation is a
   deliberate manual step the owner performs after your work is done.
2. **Never message anyone.** No test texts, no "verification" messages to real
   contacts, no Discord DMs. The test suite uses stub transports; that is the
   only sending you may cause.
3. **Never install or connect an external/hosted bot or AI service.** The
   Discord integration uses only a bot the owner already runs locally. Do not
   install Composio or any bot-hosting/connector service, do not create bot
   tokens, do not add external AI API keys or credentials of any kind.
4. **Never display secret values.** Secrets are generated by
   `scripts/generate_secrets.py` and stay in files with mode 0600. Do not
   `cat` them, print them, or include them in your output. Report paths and
   counts only.
5. **Stop before real-contact activation.** Your job ends at "installed,
   tested, outbound disabled". Return evidence; the owner takes it from there.

## Step 1 — discover the environment

Collect (do not guess): OS and Python version (`python3 --version`, need
3.10+), whether systemd user units are available, where the owner wants state
(`RECEPTIONIST_HOME`, default `~/.local/state/ai-receptionist`), whether a
BlueBubbles (or other) transport server exists and its **local** URL, whether
a local model server (e.g. Ollama) exists and its **loopback or LAN** URL, and
whether the owner runs a local Discord bot.

## Step 2 — ask only the irreducible decisions

Ask the owner exactly these questions; everything else has a safe default:

1. Business name and assistant display name?
2. State directory (default fine?)
3. Transport: BlueBubbles server URL (local), or "none yet"?
4. Local model endpoints for Tier-2 text and vision, or "none" (the service
   degrades to deterministic replies and fail-closed image handling)?
5. Discord mirror: enabled? If yes: guild ID, owner user ID, bot user ID,
   intake channel ID, category channel IDs (owner creates the private
   channels with their own bot; you never do).

**Never ask for — and never accept into chat — the owner's phone number or
email address.** Tier-3 owner-line enrollment (step 4) uses a local no-echo
prompt that only the owner types into, so the address never enters your
conversation, your context window, your logs, or shell history. If the owner
pastes an address into chat anyway, do not use, store, or repeat it; ask them
to enter it at the step-4 prompt instead.

## Step 3 — install and test

```bash
./scripts/install.sh
```

This generates secrets (not displayed), writes a starter config (loopback
bind, outbound disabled, Discord disabled), renders the systemd unit template,
and runs the full offline test suite. All tests must pass. If any fail, fix
the environment (not the assertions) and rerun.

Edit `<state>/config.json` with the answers from step 2. Validate:

```bash
./scripts/doctor.sh
```

## Step 4 — the owner registers their line (fingerprint only)

Ask **the owner** to run this command themselves, in their own terminal, and
to type their phone/email at the no-echo prompt. Do not ask them to tell you
the address, do not run the prompt on their behalf with a value from chat,
and do not read it back afterward — the value must never appear in your
conversation, output, logs, shell history, or the process table:

```bash
python3 scripts/generate_secrets.py --add-tier3
# the owner types the address at the hidden prompt; it is not echoed
```

The raw address is fingerprinted with the local `contact_hash_key` and only
the fingerprint is stored. Your evidence may state that Tier-3 enrollment was
completed — never the address itself.

## Step 5 — run the security battery

```bash
./scripts/verify.sh
```

This runs every unit, abuse, and synthetic end-to-end test with a network
guard that fails any test attempting a non-loopback connection. All tests must
pass and the run must print `VERIFY_OK=True`.

## Step 6 — optional integrations (still no activation)

- Discord: follow `docs/DISCORD.md` (config only; the owner's local bot does
  the posting).
- Hermes gateway: follow `docs/HERMES-INTEGRATION.md` (render → verify →
  apply on the owner's checkout; every step fails closed on drift).

## Step 7 — report evidence and stop

Report ONLY: paths created, test counts (e.g. "N tests, all passed"),
`DOCTOR_OK`/`VERIFY_OK` lines, and config keys you changed (names, not secret
values). Explicitly state: "Outbound is disabled; no contact was messaged; no
external service was installed. Live activation is the owner's manual step:
set `outbound.enabled: true` in config.json after reading
docs/OPERATOR-GUIDE.md, then restart the service."

Then stop.
